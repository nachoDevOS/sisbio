## Trabajo 1 — Limpiar las marcaciones del equipo biométrico

**Commit:** `(pendiente de commit)` — mensaje sugerido: `feat(equipos): limpiar el buffer de marcaciones del reloj desde el listado`

### Problema
No había forma de vaciar la memoria de marcaciones de un equipo desde el
sistema. Cuando el buffer del reloj se llena, el equipo deja de guardar
registros nuevos y hay que limpiarlo a mano en el dispositivo.

### Archivos modificados
| Archivo | Cambio |
|---|---|
| `device-service/main.py` | **Nuevo endpoint** `POST /device/attendance/clear`: `clear_attendance()` de pyzk, con el mismo reintento TCP→UDP, `disable_device()` mientras borra y cierre garantizado que el resto. |
| `app/Services/DeviceService.php` | Nuevo `clearAttendance()`. `get()` y `post()` pasan a compartir un `peticion()` privado. |
| `app/Http/Controllers/EquipoController.php` | Nuevo `limpiarMarcaciones()`, autorizado con `delete` sobre el equipo. |
| `routes/web.php` | `POST equipos/{equipo}/marcaciones/limpiar`. |
| `resources/views/equipos/index.blade.php` | Opción «Limpiar marcaciones» en el menú **Mas**, con modal propio. |
| `device-service/README.md` | El endpoint nuevo en la tabla de rutas. |
| `tests/Feature/{EquipoController,DeviceService}Test.php` | Pruebas del flujo y del cliente HTTP. |

### Solución
Solo se borran las **marcaciones**. Los usuarios, huellas, rostros y tarjetas
registrados en el equipo quedan intactos, y la asistencia que ya está en la base
del SIA tampoco se toca.

Una limitación del protocolo condicionó todo el diseño: ZKTeco solo ofrece
`clear_attendance()`, que **vacía el buffer entero**. No existe borrado por rango
de fechas. Por eso el modal no tiene selector de fechas, avisa que se va todo el
historial y exige escribir la palabra `LIMPIAR` para habilitar el botón — en vez
del `confirm()` simple que usa el resto del sistema, porque acá se destruye
información de un aparato físico y no hay vuelta atrás.

El POST manda los datos del equipo por *query string* y no en el cuerpo: el
microservicio declara todos sus parámetros como `Query(...)`.

## Trabajo 2 — Fix: «No se pudo limpiar: Not Found» en el primer uso

**Commit:** `(sin cambios de código)`

### Problema
Al usar el botón por primera vez, el sistema respondía:

```
No se pudo limpiar: Not Found
```

### Solución
No era un error del código. El microservicio Python corría con
`python -m uvicorn main:app --host 127.0.0.1 --port 9001`, **sin `--reload`**, así
que el proceso tenía cargado en memoria el `main.py` anterior, sin el endpoint
nuevo. Laravel pegaba a una ruta inexistente, FastAPI devolvía 404 y el mensaje
llegaba como «Not Found».

Se confirmó consultando el `openapi.json` del proceso vivo, que listaba solo las
tres rutas viejas. Se reinició el servicio y quedó resuelto.

### Verificación
| Prueba | Antes | Después |
|---|---|---|
| `/openapi.json` | 3 rutas | 4 rutas (aparece `/device/attendance/clear`) |
| `POST` sin token | — | `401` |
| `POST` con token, IP `192.0.2.1` | `404` | `503` (equipo inalcanzable) |

Se usó `192.0.2.1` (rango TEST-NET, no ruteable) a propósito: comprueba que la
ruta responde sin tocar ningún biométrico real.

> **Para tener en cuenta:** cada vez que se edite `device-service/main.py` hay que
> reiniciar uvicorn a mano. Si se quiere que recargue solo en desarrollo, se
> arranca con `--reload`.

## Trabajo 3 — Respaldo automático en CSV antes de borrar

**Commit:** `(pendiente de commit)` — mensaje sugerido: `feat(equipos): descargar el respaldo completo antes de vaciar el reloj`

### Problema
Vaciar el reloj es irreversible y el modal solo *sugería* exportar antes. Si el
operador se salteaba ese paso, el historial se perdía.

### Archivos modificados
| Archivo | Cambio |
|---|---|
| `resources/views/equipos/index.blade.php` | Nuevo `respaldarYLimpiar()`: descarga el CSV completo y recién después envía el borrado. Nuevo `fechaHoy()`. |
| `tests/Feature/EquipoControllerTest.php` | Dos pruebas: el modal usa el respaldo, y el export sin rango no manda `desde`/`hasta`. |

### Solución
El botón pasó a llamarse **«Descargar todo y borrar»** y encadena los dos pasos:

1. Pide el export **sin `desde`/`hasta`**, que trae el historial completo — lo
   mismo que se está por borrar.
2. Dispara la descarga del archivo.
3. Espera 1,5 s y recién entonces envía el POST de borrado.

**Si la descarga falla, no se borra nada:** un `return` temprano corta antes de
tocar el formulario, así que un equipo caído, el microservicio abajo o un corte
de red dejan el reloj intacto y muestran el error en el modal.

La espera de 1,5 s es deliberada: el POST recarga la página, y una descarga
recién disparada puede quedar cancelada por la navegación — se borraría el equipo
sin que el respaldo llegara al disco.

**Nombre del archivo.** Quedó `respaldo-<equipo>-<fecha>.csv`, con la palabra
adelante para que todos los respaldos queden juntos al ordenar la carpeta de
descargas:

```
respaldo-iclock-entrada-2026-07-27.csv
```

Se distingue del export normal, que sigue siendo
`marcaciones-iclock-entrada-2026-07-27.csv`. La fecha se calcula en hora
**local** y no con `toISOString()` (que da UTC): en Bolivia, UTC-4, eso ponía el
día siguiente a partir de las 20:00.

## Trabajo 4 — Fix: una comilla doble volcaba el JavaScript en la tabla

**Commit:** `(pendiente de commit)` — mensaje sugerido: `fix(equipos): sacar las comillas dobles del x-data del dropdown`

### Problema
El listado de equipos apareció con código JavaScript impreso como texto dentro de
la columna de acciones, en cada fila:

```
{ URL.revokeObjectURL(enlace.href); this.$refs.formLimpiar.submit(); }, 1500); }
catch (e) { this.errorLimpiar = 'No se pudo descargar el respaldo…
```

### Archivos modificados
| Archivo | Cambio |
|---|---|
| `resources/views/equipos/index.blade.php` | Se quitaron las comillas dobles del comentario y se dejó una nota para que no vuelva a pasar. |
| `tests/Feature/EquipoControllerTest.php` | Prueba de regresión que mira el **texto renderizado**, no el HTML. |

### Solución
La causa fue un comentario dentro del atributo `x-data="{ … }"` que decía
`// … con "respaldo" adelante:`. Todo el componente Alpine vive dentro de ese
atributo, así que la comilla doble lo cerró; el navegador siguió leyendo hasta el
`>` de `setTimeout(() =>` y volcó el resto del bloque como texto.

Las pruebas anteriores no lo detectaron porque usaban `assertSee()`, que busca en
el HTML crudo: el JavaScript **estaba** en la página, solo que como texto visible,
y la aserción pasaba igual. La prueba nueva parsea la respuesta con `DOMDocument`
y verifica que `revokeObjectURL`, `$refs.formLimpiar` y `this.respaldando` no
aparezcan como contenido visible.

### Verificación
Se comprobó que la prueba sirve reintroduciendo la comilla a propósito:

```
Expecting 'Equ… ' not to contain 'revokeObjectURL'.
```

> **Deuda técnica:** ese `x-data` ya lleva unas 90 líneas de JavaScript dentro de
> un atributo HTML, y este error es consecuencia directa de eso. Conviene moverlo
> a un `Alpine.data('equipoAcciones', …)` en un `<script>`, donde las comillas
> dobles dejan de importar.

## Trabajo 5 — Bitácora de equipos y motivo obligatorio

**Commit:** `(pendiente de commit)` — mensaje sugerido: `feat(equipos): bitácora de acciones sobre las marcaciones con motivo obligatorio`

### Problema
Las cuatro acciones que tocan las marcaciones de un equipo —exportar, enviar a la
base del SIA, limpiar el reloj y dar de baja el equipo— no dejaban rastro. No se
podía saber quién había vaciado un biométrico, cuándo ni por qué.

### Archivos modificados
| Archivo | Cambio |
|---|---|
| `database/migrations/2026_07_27_160605_create_equipo_auditorias_table.php` | **Nueva:** tabla `equipo_auditorias`. |
| `app/Models/EquipoAuditoria.php` | **Nuevo:** constantes de acción, `registrar()` y la foto del equipo. |
| `database/factories/EquipoAuditoriaFactory.php` | **Nueva:** con estados `limpieza()` y `baja()`. |
| `app/Http/Controllers/EquipoController.php` | Las 4 acciones anotan en la bitácora; `destroy()` y `limpiarMarcaciones()` exigen motivo; nuevo `auditoria()` para la pantalla. |
| `routes/web.php` | `GET equipos/auditoria`, antes del `resource` para que `{equipo}` no capture la palabra. |
| `resources/views/equipos/auditoria.blade.php` | **Nueva:** pantalla de la bitácora, con filtro por acción y buscador. |
| `resources/views/equipos/index.blade.php` | Botón **Bitácora** en la cabecera; modal de baja con motivo; campo de motivo en el de limpieza. |
| `resources/views/layouts/app.blade.php` | `.campo textarea` sumado a los estilos de formulario (no estaba). |
| `tests/Feature/EquipoControllerTest.php` | 11 pruebas nuevas de bitácora y motivo. |

### Solución
Cada acción anota una fila con **quién, qué, cuándo, desde qué IP y por qué**.

| Acción | Motivo | Qué más guarda |
|---|---|---|
| Exportó CSV | no pide | rango pedido y cantidad de marcaciones |
| Envió a la BD | no pide | rango, cantidad y el resultado del cruce |
| Limpió el equipo | **obligatorio** | — |
| Eliminó el equipo | **obligatorio** | — |

Dos decisiones de diseño:

- **Se guarda una foto del equipo, no un join.** La columna `datos_equipo` (JSON)
  copia nombre, IP, puerto, ubicación y algoritmo tal como estaban en ese
  momento. Si después le cambian la IP o dan de baja el equipo, la bitácora
  sigue mostrando cómo estaba cuando se hizo la acción. Se omite `comm_key` a
  propósito: es la contraseña del reloj y no tiene por qué duplicarse en una
  tabla que se lee desde una pantalla.
- **También se registran los intentos fallidos**, con `exito = false` y el
  mensaje de error. Un equipo que no respondió es información de auditoría igual
  de válida que uno que sí.

El motivo se valida en el servidor (`required|min:5|max:500`), no solo en el
formulario. En el borrado del equipo viaja como `deleteObservacion`, así que el
trait `RegistersUserEvents` lo guarda además en la propia fila de `equipos`
junto con `deleteUser_id`.

La pantalla se abre con el botón **Bitácora** del listado de equipos y está
protegida con el permiso `ViewAny:Equipo`, que ya existía: no hace falta tocar la
matriz de roles.

## Trabajo 6 — El menú distingue las acciones que borran

**Commit:** `(pendiente de commit)` — mensaje sugerido: `fix(equipos): rotular y separar las acciones destructivas del menú`

### Problema
En el menú **Mas** las tres opciones se veían casi iguales. «Limpiar
marcaciones» quedaba pegada a «Exportar marcaciones» y el nombre no daba a
entender que borra el historial del reloj: «limpiar» suena a mantenimiento, no a
borrado irreversible.

### Archivos modificados
| Archivo | Cambio |
|---|---|
| `resources/views/equipos/index.blade.php` | Separador + rótulo **BORRAR** antes de las dos acciones destructivas; «Limpiar marcaciones» pasa a «Borrar marcaciones del equipo» con ícono de borrado. |
| `resources/views/layouts/app.blade.php` | Estilos `.dropdown-menu__separador` y `.dropdown-menu__grupo`; las opciones `.peligro` van en negrita y con fondo rojo al pasar el mouse. |
| `tests/Feature/EquipoControllerTest.php` | La prueba del menú verifica el texto nuevo. |

### Solución
Las dos acciones que destruyen información quedan agrupadas debajo de una línea
divisoria y del rótulo **BORRAR**, separadas de la exportación:

```
  Exportar marcaciones
  ─────────────────────────────
  BORRAR
  Borrar marcaciones del equipo
  Eliminar equipo
```

El ícono de «Borrar marcaciones» pasó de una tecla de retroceso a una caja de
archivo tachada, que se lee como borrado de registros y sigue distinguiéndose del
tacho de basura de «Eliminar equipo». La ruta y el resto del código siguen
llamándose `limpiar`: el cambio es solo de nombre visible.

## Trabajo 7 — Rediseño del modal de exportación

**Commit:** `(pendiente de commit)` — mensaje sugerido: `feat(equipos): rediseñar el modal de marcaciones con acciones explicadas y atajos de rango`

### Problema
El modal metía tres botones (Cancelar, Descargar CSV, Enviar a la BD) en 24 rem:
se partían en dos filas y quedaban desalineados. Peor que lo estético: los dos
botones de acción se veían casi iguales y no había forma de saber que uno baja un
archivo y el otro **graba en la base del SIA**, que es lo que de verdad importa.

### Archivos modificados
| Archivo | Cambio |
|---|---|
| `resources/views/equipos/index.blade.php` | Acciones como bloques explicados, atajos de rango y «Cancelar» como enlace. Nuevos `aIso()`, `rangoUltimos()`, `rangoEsteMes()` y `rangoMesPasado()`. |
| `resources/views/layouts/app.blade.php` | Estilos `.modal-caja--ancha`, `.modal-bajada`, `.rangos-rapidos`, `.modal-opcion*`, `.modal-pie` y `.enlace-cancelar`. |
| `tests/Feature/EquipoControllerTest.php` | La prueba del modal verifica los textos explicativos. |

### Solución
Cada acción pasó a ser un bloque que dice qué hace:

```
Marcaciones de «ZKTECO Prueba»
Elegí el rango y después qué hacer con esas marcaciones.

Desde [01/07/2026]        Hasta [27/07/2026]
( Hoy ) ( Últimos 7 días ) ( Este mes ) ( Mes pasado )

┌ ↓  Descargar CSV ──────────────────────────────────┐
│    Baja un archivo a tu computadora. No modifica   │
│    nada.                                            │
├ ↑  Enviar a la base del SIA ───────────────────────┤
│    Registra las marcaciones en el sistema. No baja │
│    ningún archivo.                                  │
└────────────────────────────────────────────────────┘
                                            Cancelar
```

El ancho pasó de 24 a 30 rem, «Cancelar» dejó de competir como botón y quedó
como enlace al pie, y se agregaron cuatro atajos de rango para no tipear las dos
fechas en los casos de siempre. El de «Mes pasado» usa el truco del día 0
(`new Date(año, mes, 0)` = último día del mes anterior), así funciona con meses
de 28, 30 y 31 días sin casos especiales.

Los cálculos de fecha usan hora local, no `toISOString()`, por el mismo motivo
del Trabajo 3.

## Informe para presentación (copiar/pegar en Word)

**Informe de trabajo — 27/07/2026**
**Responsable:** nachoDev

**Actividad:** Se agregó al sistema la posibilidad de **limpiar la memoria de los
equipos biométricos** y un **registro de control** de todo lo que se hace con la
información de esos equipos.

**Problema detectado:**
Cuando la memoria de un reloj biométrico se llena, el equipo deja de guardar
marcaciones nuevas. Hasta ahora había que vaciarlo manualmente en el aparato, y
no quedaba ninguna constancia de quién lo había hecho ni por qué. Lo mismo
ocurría con las descargas de marcaciones y con las bajas de equipos: cualquier
usuario con permiso podía hacerlo sin dejar rastro.

**Solución aplicada:**
1. **Limpieza desde el sistema:** desde el listado de equipos se puede vaciar la
   memoria de marcaciones de un biométrico, sin ir hasta el aparato.
2. **Respaldo obligatorio:** antes de borrar, el sistema descarga solo un archivo
   Excel/CSV con todo el historial del equipo. Si esa descarga falla, **no se
   borra nada**. El archivo se guarda con un nombre claro, por ejemplo
   `respaldo-iclock-entrada-2026-07-27.csv`.
3. **Doble confirmación:** para borrar hay que escribir la palabra LIMPIAR y
   explicar por qué se hace. Es una acción que no se puede deshacer.
4. **Solo se borran las marcaciones:** las huellas, los rostros y los usuarios
   registrados en el equipo no se tocan, y la información que ya está en la base
   del sistema tampoco.
5. **Registro de control (bitácora):** el sistema ahora anota quién descargó
   marcaciones, quién las envió a la base, quién limpió un equipo y quién dio de
   baja un equipo, con la fecha, la hora, la computadora desde la que se hizo y
   el motivo escrito. Se consulta desde el botón «Bitácora» del listado de
   equipos y se puede filtrar por tipo de acción o buscar por equipo, usuario o
   motivo.
6. **La bitácora no se pierde:** guarda una copia de los datos del equipo (nombre,
   IP, ubicación) tal como estaban en ese momento, así que sigue siendo legible
   aunque después se cambie o se dé de baja el equipo. También quedan anotados
   los intentos que fallaron.

**Correcciones hechas en el camino:**
- La primera vez que se usó el botón, el sistema respondió «No se pudo limpiar:
  Not Found». No era un error del programa: el servicio que se comunica con los
  biométricos seguía funcionando con la versión anterior en memoria y había que
  reiniciarlo. Resuelto y verificado.
- El listado de equipos mostró texto de programación dentro de la tabla por un
  error de escritura en el código. Corregido, y se agregó una prueba automática
  que detecta ese problema si vuelve a ocurrir.

**Resultado:** Los equipos biométricos se pueden mantener desde el sistema, sin
riesgo de perder información —siempre queda el respaldo— y con un registro
completo de quién hizo cada cosa y por qué. Las pruebas automáticas pasaron de
223 a 251, con las mismas 6 falladas de otros módulos ya identificadas.
